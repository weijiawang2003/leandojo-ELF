# Mini-ELF v13 — Failure Examples (annotated)

Concrete failing rows after the v13 warm-verifier rerun. Each entry
shows what the model emitted, what lean said (after the warm rerun),
why each candidate failed, and what — if anything — v14 could do
about it. Companion to `V13_TIMEOUT_RERUN_REPORT.md`.

---

## 1. forall_inst_var_m — the only forall_inst row v13 cannot fix

* **Theorem.** `(m : Nat) (h : ∀ x : Nat, x = m) : 8 = m`
* **Goal literal.** `8`
* **Pass@5 outcome.** v12 = FAIL, v13 warm rerun = FAIL (unchanged).

The literal-aware decode gate requires *some* candidate in the beam
matching the `exact <ident> <num>` shape so it can substitute the
goal literal `8`. The v11 beam for this row contains no such
candidate; instead it is dominated by char-level truncations:

```
rank 0: 'exact h'        — type-mismatch error
rank 1: 'refine hq ='    — parse fail (unexpected end of input)
rank 2: 'rcases h wi'    — char-truncation: 'with' clipped to 'wi'
rank 3: 'refine hq'      — unknown identifier 'hq'
rank 4: 'refine hq⟩'     — unknown identifier 'hq'
rank 5: 'refin rfl⟩'     — char-truncation: 'refine' clipped to 'refin'
rank 6: 'refintro hn'    — fused token: 'refine' + 'intro' (and timeout in v12)
rank 7: 'rwexact h'      — fused token: 'rw' + 'exact'
rank 8: 'refintro hq'    — fused token, again
rank 9: 'refine ⟨m,'     — parse fail (unbalanced bracket)
```

**Why warm-rerun doesn't help.** Only `refintro hn` was originally
`timeout` (the rest were "real" failures). After the warm rerun it
becomes `unknown tactic` (the proper error). No new candidate is
generated by the rerun.

**Why a tokenizer would help.** A token-level decoder cannot emit
`refintro` because `refine` and `intro` are two distinct keyword
tokens; it cannot emit `rwexact` because `rw` and `exact` are two
keywords; and it cannot emit `rcases h wi` mid-word because `with`
is a closed keyword that the model would either choose whole or
not at all. The v13 tokenizer module is the prerequisite — the
retrain itself is deferred to v14.

## 2. exists_reconstruct_3 — unknown-identifier `m` (already passes via siblings)

* **Theorem.** `(h : ∃ n : Nat, n = 3) : ∃ m : Nat, m = 3`
* **Candidate.** `cases h with | intro n hn => exact ⟨m, hn⟩`
* **v12.** timeout. **v13.** `error: unknown identifier 'm'`.
* **Row pass@5 outcome.** PASS (a different beam candidate verifies),
  so this does not move headline metrics.

The candidate references `m` (presumably copied from the goal's
`∃ m`) but `m` is never introduced by `cases h with | intro n hn`
— that pattern binds `n` and `hn`. The semantically correct rewrite
would be `exact ⟨n, hn⟩` (witness `n`) or `exact ⟨3, rfl⟩` (witness
`3`).

**Diagnosis class.** Witness-construction bug. Not a tokenizer issue;
the candidate is syntactically valid. A future learned reranker
could in principle penalise unknown-identifier patterns, but a more
principled fix is teaching the decoder that `cases … | intro n hn =>`
binds `n`, not `m`.

## 3. forall_inst_13_6 rank-4 `exact h` — the type-mismatch under the timeout

* **Theorem.** `(h : ∀ x : Nat, x = 6) : 13 = 6`
* **Candidate at rank 4.** `exact h`
* **v12.** timeout. **v13.** `error: Type mismatch | h | has type | ∀ x : Nat, x = 6 | but is expected to have type | 13 = 6`.

This is interesting because v12 reported this as `timeout` even
though the elaboration finishes quickly under a warm verifier and
*always* fails with a type error. The 20-s cap fired before lean
could emit the diagnostic; the warm rerun reveals the underlying
error in <500 ms.

**Lesson.** When the diagnostic budget is tight, v12-style
`timeout` markings overstate the cost of *real* failures.

## 4. forall_inst_3_0 rank-6 `exact h 4` — wrong literal substitution

* **Theorem.** `(h : ∀ x : Nat, x = 0) : 3 = 0`
* **Candidate at rank 6.** `exact h 4`
* **v12.** timeout. **v13.** `error: Type mismatch | h 4 | has type | 4 = 0 | but expected to have type | 3 = 0`.
* **Row pass@5 outcome.** PASS (rank 0 `exact h 3` verifies).

The model picked the wrong numeric literal (`4` instead of `3`). v12's
literal-adapt module is exactly designed to fix this kind of
mistake — it generates the literal-substituted version and lets the
reranker promote it. In this row that worked: the rank-0 candidate
is the verifying one, so the rank-6 stale-literal is harmless. The
v13 warm rerun simply exposes its diagnostic so the failure class is
clear in audit logs.

## 5. forall_inst_var_k rank-7 `rcases h with hn => exact h` — unsolved goals

* **Theorem.** `(k : Nat) (h : ∀ x : Nat, x = k) : 8 = k`
* **Candidate at rank 7.** `rcases h with hn => exact h`
* **v12.** timeout. **v13.** `error: unsolved goals` (the `rcases`
  pattern binds an explicit hypothesis from a non-inductive value,
  which Lean accepts trivially, then `exact h` doesn't type-match).
* **Row pass@5 outcome.** PASS in v13 (rank 0 `exact h 8` verifies
  after warm rerun).

**Diagnosis class.** Semantic — the model produced syntactically
valid Lean that doesn't close the goal. Not a tokenizer fix.
